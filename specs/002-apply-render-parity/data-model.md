# Data Model: Apply Template Rendering Parity

## Existing inputs and relationships

`ManifestSource` owns ordered manifest paths, resource instances, values, secrets, and explicit `rio` template context. `ApplierOptions.scope` owns the operation's organization/project identifiers. Both facades call the shared preparation path during construction. Each parsed manifest becomes a `PreparedResource` with a source location, raw parsed `source_data`, validated resource model, and identity. `InspectionResult` returns copies for callers.

```text
ManifestSource + ApplierOptions.scope
              │
              ▼
       Render context + filters
              │
              ▼
        Parsed documents ──────► RenderedDocument[]
              │                       │
              ▼                       ▼
      Validated resources       InspectionResult
```

## ManifestSource addition

| Field | Type | Rule |
|-------|------|------|
| `interface_resolver` | `DeviceInterfaceResolver | None` | Optional caller owned synchronous resolver. Omitted unless a template needs `get_intf_ip`. Held by reference; callers are responsible for its own state and readiness. |

`DeviceInterfaceResolver` is a public callable or Protocol accepting `(project_guid: str, device_name: str)` and returning `Mapping[str, Sequence[str]]`. The SDK invokes it with the explicit project GUID from `ApplierOptions.scope`. The return maps interface names to ordered address lists. Both facades use it during common construction. It is not a platform client, and ordinary rendering never calls it.

The resolver may raise for a missing device, unreadiness, or lookup failure; preparation converts that to a source attributed template error. A wrong return shape also fails preparation. A resolver doing I/O blocks construction, so async users should prefetch ready interface data or supply an in-memory resolver.

## Render context

| Field | Source | Validation/use |
|-------|--------|----------------|
| Values | `ManifestSource.values` | Existing ordered deep merge. |
| Secrets | `ManifestSource.secrets` | Existing explicit namespace behavior. |
| Rio | `ManifestSource.rio` | Existing explicit template namespace; a present `rio.project.guid` must agree with the explicit scope when `get_intf_ip` is used. |
| Project scope | `ApplierOptions.scope.project_guid` | Required only when `get_intf_ip` is invoked. |
| Environment | Process environment at preparation time | Read by `getenv`; a present empty variable remains empty. |
| Device addresses | Resolver result | Read only by `get_intf_ip`, using interface order from the template. |

## RenderedDocument addition

| Field | Type | Rule |
|-------|------|------|
| `source` | `SourceLocation` | File/document or resource instance attribution. |
| `data` | `dict[str, Any]` | Deep copied parsed document before resource model normalization for file inputs; for caller supplied resource instances, a deep copied model representation. String top-level keys are required. Values preserve YAML/JSON scalar types and list order. |

`InspectionResult.rendered_documents: tuple[RenderedDocument, ...]` uses the same input order as the existing `resolved_manifests`. Each entry corresponds to one nonempty resource document. `RenderedDocument.data` is independent of internal prepared state and of the returned validated model. Empty YAML documents do not appear. The existing `resolved_manifests` field remains the validated model view.

## Reference fixture and parity case

| Entity | Fields | Rule |
|--------|--------|------|
| Reference fixture | Structured CLI output documents, ordered | Captured before SDK comparison; not generated by SDK. |
| Fixture provenance | CLI/chart commit, installed Ansible/Jinja versions, template paths and hashes, values, rio context, environment, device response, capture command | Reproduction must not require a live account. |
| Parity case | Chart name, case name, source templates, one merged value mapping, expected documents | Exactly two or more cases per chart. Document count, order, values, list order, and scalar types must match. |

## State and failure transitions

1. Construct source and options. Inputs are snapshotted as before; the resolver remains a caller owned callable reference.
2. Build the filter registry and render each file. Ansible support failures and template errors are attributed to the file being prepared.
3. If `get_intf_ip` is evaluated, require project scope and resolver, resolve device interfaces, then choose the first available candidate address. Missing or invalid information raises `ApplierValidationError(category="template")` with the file source.
4. Parse YAML/JSON, validate the resource, and retain both raw parsed document and validated model.
5. Return deep copied raw documents and models from `inspect()`. Apply/delete remains unavailable if construction failed.

No platform mutation occurs in these transitions.
